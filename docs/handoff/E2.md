## Deviations and choices

Each is within the owner decisions and §18; the merge stage folds them into §18.8 / §18.14 (request M-1).

- **E2-D1. The kind is read by a hand-written visitor, not a derived struct.** §18.8 says "small `Deserialize`
  structs". The envelope, document, page and object levels are derived; the kind is not, because a derived visitor
  fails on any repeated known key, and `geom` or `embed` can repeat legally in a kind whose model does not know them (a
  pen: both engines accept it). With a derived kind such a board would either be refused (both `embed` and the
  refusal look the same) or, as "any other failure", lose all its links. The visitor counts `embed` keys and refuses
  only when `type` is `"box"`, whatever the key order. Keys and strings are unescaped as serde does (`"bo\u0078"` is a
  box, `"emb\u0065d"` is the key `embed`), so the scan sees what both engines see.
- **E2-D2. A repeated `item` inside `embed` keeps its last value**, as a `serde_json::Value` does, which is how §18.3
  says the patched engine reads `embed` ("the deserializer reads the value as a `serde_json::Value`"). A repeated
  `item` is no repeated `embed` key, so it is not refused. Request E1-1 checks the engine agrees.
- **E2-D3. An object whose id repeats an earlier one on its page is not linked.** `serial::sanitize` keeps the first
  object of an id and drops the rest, so the engine never shows such a card and drops it on its next save. The
  repeated-`embed` refusal still applies to it (the engine's deserializer fails before `sanitize` runs).
- **E2-D4. The scan reads every page and layer**, hidden or locked ones included (the engine's `items` does the same);
  the cap of 1000 counts distinct canonical targets in first-appearance order, and the board's own id is skipped by
  the store, so a board whose own id is among its first 1000 targets gets 999 rows.
- **E2-D5. Initializers replace the links.** `clear` (used by `init_with`, `init_empty` through `store_initial`, and
  `copy`) deletes the item's `embed` rows, so every initializer leaves exactly the links of the body it stores; `copy`
  then copies the source's rows (as `docs::copy` does) rather than scanning the body again. One exception (review
  R-4): a card of the source that targets the source itself has no row there, so the copy has no `(copy, source)` row
  either, although a save of the same body to the copy would record one.
- **E2-D6. `copy` leaves out a link from the copy to itself** (`target_id <> to`), the board-never-links-itself rule;
  it cannot happen through `items::duplicate` (the copy's id is new) but `copy` is public.
- **E2-D7. `discard_empty`'s order and message.** The existing checks (age, children, title, body) run first with
  their message unchanged; the `embed` check runs last, so only an item that would otherwise be discarded gets the
  new message. Links of kind `mention` and `link` do not keep an item (tested). A link from a source in the trash
  still keeps the item (the source can be restored); a purged source's rows are gone (`source_id` cascades).
- **E2-D8. Additive public API** (R3): `quire_core::board::{embeds, is_canonical_uuid, EMBED_LINKS_MAX}`,
  `Inspect::embeds`, `quire_store::boards::Prepared::embeds()`.
- **E2-D9. Scenario 12 runs the AGENTS.md recipe as written.** Step 10 extracts the `sh` block that follows the HTML
  comment `<!-- e2e/agent/scenarios/12-board-embeds.sh runs the next block as it is written … -->` in `docs/AGENTS.md`
  and sources it with a `quire` shell function that forwards to the harness's runner (so it works with the CLI in the
  container and with `QUIRE_AGENT_CLI`). The recipe reads only `$B` and `$DOC`, writes `got.json` and `board.json` in
  the scenario's results directory, and sends the board on stdin (`board put "$B" - … < board.json`). Step 11 runs the
  same recipe for the empty document, which also checks the "Untitled" label branch. Anyone editing AGENTS.md §8 must
  keep the marker and a complete block after it (request M-2).
- **E2-D10. Scenario details.** Step 2 replaces the placeholders with `jq walk`; step 3 compares `jq -S` of the GET's
  content with the sent board renamed; step 4's search is limited to the scratch collection; step 6 checks the content
  type with `--out /tmp/agent-e12-p0.svg` (as 04 does) and reads the SVG text with `q_raw` (stdout without `--json`);
  steps 7 and 10 compare the canonical targets (`not-a-uuid` is a card by §18.2 but never linked); step 9 also checks
  the board's ETag did not change.
- **E2-D11. The recipe's card** is placed to the right of the page's existing frames (`max(x + w) + 40`, at `y`
  −180), or centred on the origin on an empty page, on the first visible unlocked layer, with a `card-<µs time>` id
  (jq's `now`, so no `date +%N`); numbers are written as jq integers (`480`, not `480.0`), which the engine reads and
  rewrites as floats on its next save.

## Follow-ups

- **Boards saved before M1.1** have no `embed` rows until their next save (no schema change, R5, and no backfill).
  Cards could only be written by API clients then, so this is unlikely; a backfill (scan every board at startup or in
  `admin check`) would be a small migration-free job if backlinks ever need it.
- **Backlinks** (`item_links` with kind `embed`, board → document) are recorded but not served: when a backlinks route
  arrives it must filter through `shared::visible_items` (§18.12).
- The route doc comment of `DELETE /items/{id}` (`routes/items.rs`, W1) and the `discard_empty` parameter description
  (`quire-api`) still list only the old conditions, as §18.8 requires (no OpenAPI change); a later API revision could
  name the embed rule there.
